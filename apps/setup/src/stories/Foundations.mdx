### shadcn compatibility aliases — not canonical

`components/ui/button.tsx` (and any future shadcn-added component) expects `--muted`, `--accent` (plus their `-foreground` pairs), `--card`, `--popover`, `--input`, `--ring`, and `--destructive` to exist, because shadcn's generated code references them. **None of these are part of Color Foundations v1** — they carry no approved product meaning yet. They're kept defined only so existing components don't break, conservatively aliased onto the semantic tokens above. (`--secondary`/`--secondary-foreground` used to be in this bucket too — promoted to canonical 2026-08-14, see the swatch above.)

| shadcn variable | Aliased to | 
| --- | --- |
| `--muted` / `--muted-foreground` | `--surface-subtle` / `--foreground-secondary` |
| `--accent` / `--accent-foreground` | `--interactive-subtle` / `--foreground` |
| `--card`, `--popover` (+ foregrounds) | `--background` / `--foreground` (flat surfaces, no distinct card tone) |
| `--input` | `--border` |
| `--ring` | `--foreground` |
| `--destructive` | unchanged shadcn default (no red exists in v1; Paper doesn't style Discard Activity as alarming) |

Don't use these six aliases intentionally in new SetUp components, and don't treat them as approved foundations — they're a compatibility shim, not a design decision. That's also why they're not shown as swatches above.

`--chart-1` through `--chart-5` are likewise unaddressed by v1 (the weekly-graph green that used to live in `--chart-1` no longer exists in Paper — replaced with moss) and are left at shadcn's neutral placeholders.

Font: the **system UI font stack** (`--font-sans`, Tailwind's built-in default — `-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, …`), matching Paper's "System Sans-Serif" as a deliberate choice, not a webfont. Don't create a `Button`/`Chip`/`Timer`-named token even if a future component seems to want its own size — ask first.

**Always pair `text-{token}` with `leading-{token}`** (e.g. `text-action leading-action`) — never `text-{token}` alone. Confirmed 2026-08-14: on form controls (`button`, `input`, etc.), Tailwind's own Preflight `font: inherit` reset wins the line-height cascade over `text-*`'s built-in `--text-*--line-height` fallback, so a bare `text-action` silently renders at the browser's inherited line-height (24px) instead of 22px. A real `leading-*` utility reliably overrides Preflight; the auto-paired one doesn't. Each of the 9 tokens above has a matching `--leading-*` value in `index.css` for exactly this reason.

- **`radius-md`** (8px) — cards, rows, chips, stat blocks. The one surface radius in the whole product.
- **`radius-full`** (100px) — buttons, circular icon buttons, pill-shaped dividers. In practice this is Tailwind's own `rounded-full` utility (hardcoded to a very large radius, not theme-configurable) — visually identical to 100px at every size used here, so there's no separate `rounded-radius-full` class; `--radius-full` exists purely as the documented canonical value.

**Do not create `radius-sm`, `radius-lg`, `radius-xl`, or any other radius token** unless Paper introduces an actual new radius — there are only two surface treatments in this product, pill or `radius-md`, nothing in between.

**Update 2026-08-14**: `--radius-sm`/`--radius-lg`/`--radius-xl`/`--radius-2xl`/`--radius-3xl`/`--radius-4xl` (and their `--radius` seed) have been removed from `index.css`. They were legacy shadcn scaffold values kept only because Button v1's predecessor referenced `--radius-lg`; once Button v1 (see "Buttons" below) stopped using them, a full `src/` grep confirmed zero remaining consumers, so they were deleted rather than left as dead code.

## Borders

Width follows Tailwind's default scale (`border` = 1px, `border-2` = 2px) — not overridden. Two color weights, both semantic tokens: `border` (moss @ 20%) for chip outlines, `border-subtle` (moss @ 10%) for dividers and other outlines.

Paper's dividers are filled rectangles (`background-color: var(--border-subtle)` at a fixed height), not CSS borders. The day-selector chips use a real `outline` (not a fill, not a `border`) at the stronger weight — `outline: 1px solid var(--border)` — so it doesn't affect layout box size.

## Iconography

Library: **lucide-react** only (spec §14) — never emoji as icons.

Sizing is established by `components/ui/button.tsx` (Button v1): `size-5` (20px) is the default for icons inside a button, matching the exact icon dimensions measured across every button in Paper (every icon SVG is 20×20). Outside of Button, follow the same convention — `size-5` (20px) as the default, sizing down only when a specific inline-with-text context calls for it.

**Stroke width is `1.5`, not Lucide's default of `2`.** Corrected 2026-08-14 — the Button audit read Paper's raw icon markup directly (`get_jsx`, not just measured dimensions) and found every stroke-based icon uses `strokeWidth="1.5"`. An earlier version of this page said to leave Lucide's default alone; that was an unverified assumption, not a Paper measurement. Button v1 enforces this with `[&_svg]:[stroke-width:1.5]` on its base classes — outside Button, set it explicitly per icon until something more central exists.

### Stroke vs. fill — approved 2026-08-14

**Default icon** — `stroke="currentColor"`, `fill="none"` (Lucide's own default `fill`; don't override it). Color comes entirely from `currentColor`, so an icon sitting inside a colored button automatically picks up the right ink — Button never sets an icon color directly, and never will (no filled Button variants, no filled-icon color tokens, no component-specific icon colors). (Paper itself has no explicit color set on any icon yet — `currentColor` is a codebase convention, not something measured in Paper.)

**Filled workout action icon** (an approved, named exception) — `stroke="none"`, `fill="currentColor"`. This is an *icon-level* choice made where the icon is used, not a Button prop or variant — each approved filled icon decides for itself. Exactly four icons carry this treatment today:

| Icon | Lucide component | Used for |
| --- | --- | --- |
| Play | `Play` | Start Workout, Resume |
| Pause | `Pause` | Pause |
| Finish | `Square` | Finish |
| Next | `SkipForward` | Next (Active Workout) — approved 2026-08-17, same treatment as Play/Pause/Finish, but keeps its stroke (see note below) |

```tsx
<Play data-icon="inline-start" fill="currentColor" stroke="none" />
<Pause data-icon="inline-start" fill="currentColor" stroke="none" />
<Square data-icon="inline-start" fill="currentColor" stroke="none" />
<SkipForward data-icon="inline-end" fill="currentColor" stroke="currentColor" />
```

**Both props are required, not just `fill`.** Every Lucide icon component ships `stroke="currentColor"` and `stroke-width="2"` on its root `<svg>` regardless of what `fill` you pass — adding `fill="currentColor"` alone leaves a 2px outline stroke doubled on top of the fill, which Paper's equivalent icons don't have (confirmed via `get_jsx`: Paper's filled icons carry a `fill` attribute and *no* `stroke` attribute at all). `stroke="none"` removes that leftover outline.

**`SkipForward` is the one exception that keeps `stroke="currentColor"`** (corrected 2026-08-17): unlike Play/Pause/Square, which are single filled shapes, SkipForward is a filled triangle *plus* a separate stroked line (the leading bar) — Lucide draws that bar as a zero-width `<line>`, which has no fill area at all and renders only via its stroke. `stroke="none"` on the whole icon silently deletes the bar, leaving what reads as a plain `Play` triangle. `fill="currentColor"` still fills the triangle; `stroke="currentColor"` is what makes the bar visible (Button's own CSS already sets `stroke-width: 1.5` on descendant icons, so no explicit width is needed here).

Don't extend this treatment to any other icon without adding it to this table first — it's a short, named list, not a general rule for "icons that feel like actions."

This is a usage rule, not a gallery — see [lucide.dev/icons](https://lucide.dev/icons) for what's available. The rule that matters for SetUp is *when* an icon is allowed to carry meaning on its own. Per spec §16, Workout Mode has to work for someone standing, moving, and tired mid-session:

- Icon-only controls are reserved for a small set of very common, instantly-recognizable actions (back, close, pause).
- Everything else — and anything in Onboarding, Plan Settings, or a primary call-to-action — pairs the icon with a visible text label. Don't let an icon carry meaning alone if getting it wrong costs the user their workout state.

## Buttons — Button v1, approved

| `ghost-inverse` | `--interactive-subtle-inverse` | `--foreground-inverse` | Discard Activity |

**Corrected naming 2026-08-14**: `secondary` was originally named `inverse`, on the wrong assumption that it needed a dark-surface context to read. It doesn't — it's an important, lower-emphasis-than-primary action with its own moss fill/white text, sitting directly on the light Workout Mode screen. `ghost-inverse` is the only variant that actually lives on a dark/inverse surface.

No `size` prop — every Paper button is one size. Padding is icon-aware via the `data-icon="inline-start"|"inline-end"` convention on icon children (see `button.stories.tsx`): no icon → `space-7` (20px) both sides; leading icon → `space-6`/`space-7` (16/20); trailing icon → `space-7`/`space-6` (20/16). Vertical padding `space-2` (6px), icon/text gap `space-5` (12px), radius `radius-full`, typography `action`. Height is a fixed `48px` (`h-12`) — approved 2026-08-14 as a direct exception to the spacing scale (no `space-*` token covers 48px); content centers in the extra space above/below the 22px line-height via `items-center`, matching Paper exactly rather than the ~34px a padding-only, content-driven height would give. Back/Settings icon-only controls are explicitly **not** part of Button v1 — see the separate `IconButton` component below. No loading state was invented — that's still out of scope.

**Resolved 2026-08-14**: `--shadow-button` approved as Shadow Foundations v1 and applied to `secondary` only — see "Shadows" above.

### Interaction states — Foundations v1, approved 2026-08-14

Default, Hover, Pressed, Focus, and Disabled are implemented for all four variants (`components/ui/button.tsx`, see `button.stories.tsx` "Interaction States" for a visual gallery). Text/icon color never changes across Default/Hover/Pressed — only background does, so contrast never degrades on interaction, and no opacity is ever applied to the whole button. Visually reviewed and approved in Storybook; canonical, not provisional.

- **`ghost`** reuses existing approved tokens for its own hover/pressed — `border-subtle` and `border`, the same moss-opacity ladder its resting state (`interactive-subtle`) already sits on. No new tokens.
- **`primary`, `secondary`, `ghost-inverse`** hover/pressed use the `--color-button-*` tokens below — Button-scoped, defined in `index.css` (raw values under `[data-slot="button"]`, mapped to Tailwind utilities in `@theme inline`). Canonical, but Button-only: don't reference them from any other component — they're interaction derivatives of Button's own fills, not general-purpose reusable surface colors.
- **Focus** ring color is conditional per variant, not a new token: `primary`/`ghost`/`secondary` ring in `foreground` (moss) — all three render directly on the light page, so a dark ring is what reads there. `ghost-inverse` rings in `foreground-inverse` (white) — the one variant that actually sits on a dark surface. 2px ring, 2px offset.
- **Disabled** never dims the whole button. `primary` and `secondary` both flatten to `ghost`'s resting visual weight (`interactive-subtle` background, `foreground-secondary` text) — both are light-surface fills, so they share the same de-emphasized target; `secondary` additionally drops `shadow-button`. `ghost`/`ghost-inverse` keep their own background and just move text to the matching `-secondary` foreground token.

## IconButton — v1, approved

**Approved 2026-08-14** in `components/ui/icon-button.tsx` — a separate component from Button, not an `icon-only` Button variant. Measured directly from Paper's "Back" button, the one fully-designed instance (present, identical, on all 5 non-`home` screens; `home` has neither Back nor Settings).

**One visual variant. No `default`/`inverse`/size/filled variants exist or should exist.** Icon color comes entirely from `currentColor`, inherited from whichever ancestor sets `text-foreground` (light surfaces) or `text-foreground-inverse` (inverse surfaces) — the exact same `<IconButton>` renders correctly in both contexts, unmodified. This mirrors exactly what Paper shows: identical 32×32 box on every instance, with only the icon's stroke color changing between the two moss-background screens (white) and the three light-background screens (moss).

| Property | Value | Token |
| --- | --- | --- |
| Width / height | 32×32px | `size-8` |
| Padding | 6px | `p-space-2` |
| Radius | full | `rounded-full` |
| Background | none | — |
| Border | none | — |
| Shadow | none | — |
| Icon size | 20×20px | `size-5` (default, same convention as Button) |
| Stroke width | 1.5 | `[stroke-width:1.5]` |
| Fill / stroke | `fill="none"`, `stroke="currentColor"` | default iconography rule — **no filled-icon exception**, Button's Play/Pause/Finish treatment does not carry over |

```tsx
<IconButton aria-label="Go back">
  <ArrowLeft />
</IconButton>
```

`aria-label` is required (TypeScript-enforced) — this is an icon-only control with no visible text. `className` is accepted for layout only (e.g. margins in a flex row); it is not meant to redefine the canonical geometry above — same documentation-only convention Button v1 already relies on, not a runtime-enforced restriction.

**Settings is out of scope for v1.** Paper contains only a hidden, empty shell for it (0×0 inner `<svg>`, no fill/stroke attributes at all, never laid into the header's flex row) — there's no designed icon to source from. Implementing it now would mean inventing an icon choice with zero Paper evidence, the same caution already applied to exercise content and training rules. Back is the only implemented use case.

### States — Default only, approved 2026-08-14

No hover/pressed/disabled visual treatment has been invented. `disabled` only gets `pointer-events-none` (behavior) — it renders **visually identical to Default**; that's intentional, not an oversight, pending a separate approval pass. Keyboard focus uses `focus-visible:ring-2 focus-visible:ring-current` — `ring-current` (not a fixed color) for the same both-contexts-for-free reason as the icon itself. No `ring-offset`: IconButton has no fill to separate the ring from, so a fixed-color offset would paint a mismatched halo on whichever backdrop (light or inverse) it sits on.

Hover / Pressed / Focus-appearance / Disabled visuals are a separate proposal, to be visually approved in Storybook — same process Button v1's interaction states went through. Don't assume Button's hover/pressed formulas transfer; IconButton's tap target and visual weight are different enough to need their own review.
